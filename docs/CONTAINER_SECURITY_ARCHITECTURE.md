# Container Security Architecture

**Document Version:** 1.0
**Last Updated:** 2026-03-24
**Audience:** Security engineers, platform engineers, DevOps teams
**Related:** [CLAUDE.md — Containerized Orchestration](../CLAUDE.md#containerized-orchestration)

## Executive Summary

The AI SDLC Orchestrator executes untrusted LLM-generated agent code within isolated Docker containers. Each orchestration run is wrapped in an ephemeral container with layered security controls:

1. **Ephemeral isolation** — `--rm` destroys all state on exit
2. **Filesystem hardening** — `--read-only` rootfs with explicit tmpfs mounts
3. **Privilege restrictions** — `--cap-drop ALL` + custom seccomp filter
4. **Resource limits** — PID, memory, CPU quotas prevent exhaustion
5. **Network segmentation** — iptables rules allow only `api.anthropic.com:443` outbound

This document explains the threat model, control design, and operational procedures.

---

## Threat Model

### Actors

1. **Untrusted LLM Agent Code** — Generated by Claude based on user feature requests; may be crafted or corrupted
2. **Malicious User Input** — Feature request text could contain injection attempts targeting the orchestrator or downstream agents
3. **Host System Operator** — Assumed trustworthy but may misconfigure container runtime

### Threats

| Threat | Severity | Description | Container Mitigation |
|--------|----------|-------------|----------------------|
| **Host Filesystem Access** | Critical | Agent reads/modifies host files outside project scope | `--read-only` rootfs; bind-mount only `runs/<run_id>/` |
| **Resource Exhaustion** | High | Fork bomb or memory leak consumes all host resources | `--pids-limit 500`; `--memory 8g`; `--cpus 4` |
| **State Persistence** | High | Prior run artifacts or Python state leaks into next run | `--rm` destroys container on exit; ephemeral tmpfs |
| **Network Exfiltration** | High | Agent steals API keys, credentials, or project data | iptables FORWARD DROP; only api.anthropic.com:443 allowed |
| **Privilege Escalation** | Medium | Agent exploits capabilities to become root or escape sandbox | `--cap-drop ALL`; custom seccomp filter |
| **Container Escape** | Medium | Agent breaks out of container to access host | seccomp blocks ptrace/mount/mknod; `--read-only` prevents rootkit |
| **DNS Exfiltration** | Medium | Agent tunnels data via DNS queries | iptables blocks DNS (port 53); IPs injected via `--add-host` |
| **Signal Hijacking** | Low | Agent sends signals to host processes | Container PID namespace isolation |

### Attack Surfaces

1. **Tool Invocation** — Agent calls tools (Claude API, shell commands, file operations); malicious tool calls could attempt unauthorized actions
2. **Feature Request String** — User input could contain shell metacharacters or injection payloads
3. **LLM Response** — Claude response could be adversarially crafted to trigger edge cases in orchestrator code
4. **Artifact Files** — Prior run artifacts written to bind-mount could be manipulated on host and read by container
5. **Environment Variables** — ANTHROPIC_API_KEY injection; env file could contain additional sensitive data

## Security Controls

### 1. Ephemeral Isolation

**Control:** `docker run --rm`

**Mechanism:**
- Container layer is destroyed on exit (success or failure)
- tmpfs mounts (`/tmp`, `/home/orchestrator/.config`) are in-memory only
- No persistent state leaks between runs

**Validation:**
```bash
# Verify container is removed after exit
docker ps -a --filter name=orchestrator- | grep -i exited && echo "FAIL: Container not cleaned" || echo "PASS"
```

**Limitations:**
- Does not protect against state leakage to host via bind-mount artifacts
- Requires `--rm` flag; if omitted, containers accumulate

### 2. Read-Only Rootfs

**Control:** `docker run --read-only --tmpfs /tmp --tmpfs /home/orchestrator/.config`

**Mechanism:**
- Container image layers are mounted read-only
- Any attempt to write to / (except tmpfs mounts) fails with "Read-only file system"
- Prevents modification of:
  - Python runtime (`/usr/local/bin/python`)
  - System libraries (`/usr/lib/`)
  - Container entrypoint (`/app/orchestrate`)

**Validation:**
```bash
# Spawn a container and attempt to touch a file outside tmpfs
docker run --rm --read-only ai-sdlc-orchestrator:latest \
  sh -c "touch /test 2>&1 || echo 'PASS: Read-only enforced'"
# Output: "PASS: Read-only enforced"
```

**Attack Prevented:**
- Rootkit installation by dropping files into `/` or `/usr`
- Modification of Python bytecode (`.pyc` files)
- Persistence via `.bashrc`, `.profile`, etc.

**Limitations:**
- Does not prevent in-memory code injection or process manipulation
- Requires explicit tmpfs mounts for legitimate writable paths

### 3. Capability Drops

**Control:** `docker run --cap-drop ALL`

**Mechanism:**
- All Linux capabilities are dropped from the container process
- Capabilities are not regained even with `sudo` (no setuid in container)
- Prevents:
  - `CAP_SYS_PTRACE` — process tracing (`ptrace(2)`, `strace`)
  - `CAP_SYS_ADMIN` — mount operations, namespace creation
  - `CAP_SYS_MODULE` — kernel module loading
  - `CAP_SETUID`, `CAP_SETGID` — user/group changes

**Validation:**
```bash
# Attempt to strace inside container (requires CAP_SYS_PTRACE)
docker run --rm --cap-drop ALL ai-sdlc-orchestrator:latest \
  sh -c "strace echo test 2>&1 | head -3"
# Output: "strace: ptrace(PTRACE_TRACEME, ...): Operation not permitted"
```

**Attack Prevented:**
- Privilege escalation via setuid binaries
- Process injection / code hijacking via `ptrace(2)`
- Kernel module loading (rootkit installation)
- Namespace escape via container migration

**Limitations:**
- Does not prevent attacks that don't require capabilities (e.g., buffer overflows)
- Some legitimate container operations require capabilities (but our use case doesn't)

### 4. Seccomp Filter (Custom)

**Control:** `--security-opt seccomp=/path/to/seccomp-profile.json`

**Mechanism:**
- Custom seccomp profile blocks dangerous syscalls beyond Docker's default
- Default Docker profile already blocks ~44 syscalls; we add explicit denials for:
  - `ptrace(32)` — process tracing (already blocked by default, re-confirmed)
  - `mount(165)` — filesystem mounting
  - `mknod(133)` — device node creation
  - `init_module(175)`, `finit_module(313)` — kernel module loading
  - `kexec_load(246)` — kernel replacement

**Profile Location:** `infra/docker/seccomp-profile.json`

**Validation:**
```bash
# Attempt mount inside container (requires syscall 165)
docker run --rm --security-opt seccomp=/path/to/seccomp-profile.json \
  ai-sdlc-orchestrator:latest \
  sh -c "mount -t tmpfs tmpfs /mnt 2>&1"
# Output: "mount: Operation not permitted"
```

**Attack Prevented:**
- Container-to-host escape via mount manipulation
- Rootkit installation via kernel module loading
- Process tracing / code injection via ptrace
- Device node creation (char device exploitation)

**Limitations:**
- Does not prevent attacks using allowed syscalls (99% of workloads only use allowed syscalls)
- Profile must be tuned to allow Python asyncio syscalls (epoll, futex, clock_gettime, etc.)
- Requires kernel version >= 3.19 (all modern systems)

### 5. AppArmor MAC (Linux only)

**Control:** `--security-opt apparmor=ai-sdlc-orchestrator` + `/etc/apparmor.d/ai-sdlc-orchestrator` profile

**Mechanism:**
- Mandatory Access Control (MAC) layer enforced by kernel
- Profile restricts:
  - **Filesystem:** Deny write except `/tmp/`, `/home/orchestrator/.config/`, `/workspace/runs/<run_id>/`
  - **Capabilities:** Deny ptrace, admin, net_raw, mknod, setuid, setgid
  - **Network:** Deny raw socket creation
  - **Docker socket:** Deny access to `/var/run/docker.sock`

**Profile Location:** `infra/docker/apparmor-profile`

**Installation (Linux only):**
```bash
sudo cp infra/docker/apparmor-profile /etc/apparmor.d/ai-sdlc-orchestrator
sudo systemctl reload apparmor
sudo apparmor_status | grep ai-sdlc-orchestrator  # Verify loaded
```

**Validation:**
```bash
# Attempt to write outside allowed paths (requires AppArmor)
docker run --rm --security-opt apparmor=ai-sdlc-orchestrator \
  ai-sdlc-orchestrator:latest \
  sh -c "touch /etc/rootkit.sh 2>&1 || echo 'PASS: AppArmor blocked'"
# Output: "PASS: AppArmor blocked"
```

**Attack Prevented:**
- Fine-grained filesystem access restriction (DAC complement)
- Network restriction (raw socket-based attacks)
- Capability-based attacks

**Limitations:**
- **Linux only** — macOS Docker Desktop has no AppArmor enforcement
- Requires profile to be loaded into kernel via `apparmor_parser`
- Audit mode vs. enforce mode (we use enforce)

### 6. PID Limit

**Control:** `docker run --pids-limit 500`

**Mechanism:**
- Container process tree cannot exceed 500 PIDs
- Fork bomb (`:(){ :|:& };:`) is killed by kernel when limit is reached
- Prevents resource exhaustion from unlimited process spawning

**Validation:**
```bash
# Attempt fork bomb (may take a few seconds)
docker run --rm --pids-limit 500 ai-sdlc-orchestrator:latest \
  sh -c ":(){ :|:& };: 2>&1 | head -1"
# Output: Will fail with "Resource temporarily unavailable" after ~500 forks
```

**Attack Prevented:**
- Fork bomb denial-of-service
- Resource exhaustion via process spawning

**Limitations:**
- Does not prevent per-process resource exhaustion (threads within one process)
- 500 PIDs is conservative; typical orchestrator run uses < 20

### 7. Memory Limit

**Control:** `docker run --memory 8g`

**Mechanism:**
- Container's memory usage capped at 8 GB
- Kernel OOM killer terminates the container if limit is exceeded
- Prevents memory exhaustion on host

**Validation:**
```bash
docker stats <container-id> --no-stream  # Monitor memory in real-time
```

**Attack Prevented:**
- Memory exhaustion DoS (malloc bombs, memory leaks)
- Swap exhaustion on host

**Limitations:**
- 8 GB limit is conservative; orchestrator typically uses 1–2 GB
- Container may be suddenly killed if limit is tight
- Swap usage is counted; swap should be disabled on host if desired

### 8. CPU Limit

**Control:** `docker run --cpus 4`

**Mechanism:**
- Container is limited to 4 CPU cores
- Prevents runaway Python processes from consuming all host CPU

**Validation:**
```bash
docker stats <container-id> --no-stream  # Monitor CPU usage
```

**Attack Prevented:**
- CPU exhaustion DoS (tight infinite loops)
- Host becoming unresponsive due to container consuming all CPU

**Limitations:**
- 4 cores is conservative for typical orchestrator work
- Does not prevent algorithmic complexity attacks (expensive operations within the limit)

### 9. Network Isolation (iptables + Bridge Network)

**Control:** `docker run --network orchestrator-net` + iptables FORWARD rules

**Mechanism:**
1. Docker bridge network `orchestrator-net` is created with:
   ```bash
   docker network create orchestrator-net
   ```

2. iptables rules are configured to:
   - Allow FORWARD from orchestrator-net to api.anthropic.com IPs on TCP 443
   - Drop all other FORWARD traffic from orchestrator-net
   - Block DNS (UDP/TCP 53) from orchestrator-net

3. DNS is disabled (port 53); instead, `--add-host api.anthropic.com=<IPs>` injects the resolved IPs at runtime

**Setup Script:** `infra/scripts/setup-network-policy.sh`

**Validation:**
```bash
# Test that api.anthropic.com is reachable
docker run --rm --network orchestrator-net ai-sdlc-orchestrator:latest \
  sh -c "curl -s --max-time 5 -o /dev/null -w '%{http_code}' https://api.anthropic.com"
# Output: 401 (Unauthorized) or 200 (API response), indicating connection succeeded

# Test that google.com is unreachable
docker run --rm --network orchestrator-net ai-sdlc-orchestrator:latest \
  sh -c "curl -s --max-time 3 https://google.com || echo 'BLOCKED (expected)'"
# Output: "BLOCKED (expected)"
```

**Attack Prevented:**
- Exfiltration to attacker-controlled servers
- SSRF attacks to cloud metadata endpoints (169.254.169.254)
- DNS tunneling (port 53 blocked)
- Unauthorized API calls to non-Anthropic endpoints

**Limitations:**
- **macOS incompatible** — Docker Desktop on macOS does not support host iptables; only seccomp and capability controls apply
- **Requires root** — Initial `setup-network-policy.sh` invocation needs sudo
- **IP rotation required** — If Anthropic rotates IPs, `setup-network-policy.sh --refresh` must be run
- **No fine-grained request filtering** — Any HTTPS request to Anthropic IPs is allowed (includes credential exfiltration if API key is compromised)

**macOS Workaround:**
Use a local HTTPS proxy with ACL:
```bash
# Install and run mitmproxy with allowlist
mitmweb --mode transparent --allowlist "api.anthropic.com"
export HTTPS_PROXY=http://127.0.0.1:8080
```

### 10. DNS Injection

**Control:** `docker run --add-host api.anthropic.com=<IPs>`

**Mechanism:**
- Resolved IPs are injected into container's `/etc/hosts` at runtime
- Blocks port 53 (DNS) so container cannot perform DNS lookups
- Prevents DNS-based data exfiltration

**Validated IPs:**
```python
# From container_runner.py: _resolve_anthropic_ips()
ips = socket.getaddrinfo("api.anthropic.com", 443, socket.AF_INET)
# Only IPv4 addresses are used (IPv6 support is future work)
```

**Attack Prevented:**
- DNS tunneling (covert data exfiltration via DNS queries)
- DNS poisoning (if container could perform DNS lookups)
- Resolution of attacker-controlled domains

**Limitations:**
- Does not prevent HTTPS-based exfiltration (only DNS)
- Requires DNS to be resolved on host before container launch
- IPv6 not currently supported

### 11. Non-Root User

**Control:** Docker image runs as UID 1000 (`orchestrator` user)

**Mechanism:**
- Dockerfile creates non-root user:
  ```dockerfile
  RUN groupadd -g 1000 orchestrator && \
      useradd -u 1000 -g orchestrator -s /sbin/nologin orchestrator
  USER orchestrator
  ```
- Container process runs as UID 1000, not UID 0 (root)
- Even with `CAP_SETUID` dropped, process cannot escalate to root

**Validation:**
```bash
docker run --rm ai-sdlc-orchestrator:latest id
# Output: uid=1000(orchestrator) gid=1000(orchestrator) groups=1000(orchestrator)
```

**Attack Prevented:**
- Privilege escalation to root via setuid binaries
- Root-only operations (mount, insmod, etc.)

**Limitations:**
- Does not prevent lateral privilege escalation within the container
- UID 1000 is arbitrary but intentional (avoids conflicts with common user UIDs)

### 12. Init Process Reaping

**Control:** `docker run --init`

**Mechanism:**
- `tini` (tiny init) runs as PID 1 instead of the orchestrate process
- Reaps zombie processes (children that have exited but parent hasn't called wait)
- Ensures clean process tree

**Attack Prevented:**
- Zombie process accumulation (resource leak)
- Signal delivery issues

**Limitations:**
- Minimal impact on security; mainly operational cleanliness

## Control Composition & Defense in Depth

| Attack Vector | Control #1 | Control #2 | Control #3 | Status |
|---|---|---|---|---|
| Host filesystem access | Read-only rootfs | Bind-mount only runs/<run_id>/ | AppArmor MAC | ✅ Defended |
| Fork bomb | PID limit | Seccomp (no new syscalls) | Capability drop | ✅ Defended |
| Rootkit installation | Seccomp (no mount/init_module) | Read-only rootfs | AppArmor MAC | ✅ Defended |
| Privilege escalation | Capability drop | Non-root user | Seccomp (no setuid) | ✅ Defended |
| Container escape | Seccomp (ptrace blocked) | Capability drop | AppArmor MAC | ✅ Defended |
| Network exfiltration | iptables rules | DNS injection | Network isolation | ✅ Defended |
| State persistence | `--rm` flag | Ephemeral tmpfs | PID namespace | ✅ Defended |

**No single control is sufficient; the combination of orthogonal controls provides robust defense.**

## Operational Procedures

### One-Time Setup

```bash
# 1. Build the Docker image
bash infra/scripts/build-image.sh

# 2. Create orchestrator-net and configure iptables (requires sudo)
sudo bash infra/scripts/setup-network-policy.sh

# 3. Load AppArmor profile (Linux only; requires sudo)
sudo bash infra/scripts/load-apparmor-profile.sh

# 4. Create secrets file
echo "ANTHROPIC_API_KEY=sk-ant-..." > ~/.orchestrator.env
chmod 600 ~/.orchestrator.env
```

### Per-Run Verification

**Before** running `orchestrate-container`:
- Verify Docker is running: `docker ps --help`
- Verify orchestrator-net exists: `docker network ls | grep orchestrator-net`
- Verify API key is set: `cat ~/.orchestrator.env | grep ANTHROPIC_API_KEY`

**After** a run completes:
- Verify container is cleaned: `docker ps -a --filter name=orchestrator- | wc -l` (should be low)
- Verify artifacts are written: `ls workspace/runs/<run_id>/artifacts/`
- Verify no forbidden files exist: `ls workspace/runs/<run_id>/`

### Maintenance

**Rebuild image after changes:**
```bash
# After modifying src/orchestrator/ or pyproject.toml
bash infra/scripts/build-image.sh
```

**Refresh network policy after Anthropic IP rotation:**
```bash
sudo bash infra/scripts/setup-network-policy.sh --refresh
```

**Diagnose stuck containers:**
```bash
# List active orchestrator containers
docker ps --filter name=orchestrator-

# Remove a stuck container
docker rm -f orchestrator-<run_id>
```

## Limitations & Gaps

### Known Limitations

1. **macOS iptables filtering** — Not applicable; egress filtering is unavailable
2. **Anthropic IP rotation** — Requires manual `setup-network-policy.sh --refresh`
3. **Stale Docker image** — Developers must remember to rebuild image after changes
4. **Container overhead** — ~2–5 seconds per run for startup
5. **No AppArmor on macOS** — Capability drops and seccomp still apply

### Future Enhancements

- [ ] Dynamic IP resolution via ipset + DNS monitoring (eliminating IP refresh requirement)
- [ ] AppArmor support for macOS (via gVisor or similar)
- [ ] Image layer caching to speed up repeated runs
- [ ] Secrets manager integration (Vault, 1Password) instead of env files
- [ ] Per-container network policies (e.g., allow specific host:port pairs)
- [ ] Performance profiling to optimize resource limits
